01 · 现状

为什么现在只扫得到 S1U#

扫描阶段的 key 匹配把机器类型提前固定了，普通服务器在进入列表之前就被丢弃。

Hub 上的 station-gateway 会扫描站点私网，但只把 SSH 主机密钥命中 NodeClass.spec.discovery.hostKeyFingerprints 的入口设备报给 Station API。线上只有 s1u 同时声明 discovery 和 access，所以 Machine 里实际只有 S1U 的 Orin。

01

扫描被 class 绑定

只有声明 discovery 的 NodeClass 才产生 key 和端口；普通服务器的 host key 不在任何 class 里，扫描不会报。

02

类型在扫描时决定

Machine.spec.nodeClass 在创建时就写死；admit 请求没有选择 class 或型号的入口。

03

节点没有类型自报

类型和型号是安装时写入的声明标签；NodeObservation 只有 NodeInfo、压力和网关状态。

关键区别 出厂指纹是共享的，不是机器身份。 它只能说明“这台入口设备看起来像同型号的未入网设备”，不能说明它是哪一台；入网后 Orin 会换成自己的 host key。用它来预分类机器人是合理的，用它来发现普通服务器则没有可预登记的 key。
02 · 目标形态

扫描先找候选，加入时再决定#

发现是证据，类型是选择；节点加入后再用观测做一致性校验，而不是把选择当成事实。

保留 S1U 的工厂指纹识别，同时增加一个可选的通用 SSH 候选通道。两类结果都落在同一张 Machine 上：有 class 的显示为机器人，没有 class 的显示为未分类。管理员在加入时选择型号或普通 SSH。

原则 1

类型不写死在扫描里

class 命中只是“默认建议”。未分类候选的 Machine.spec.nodeClass 保持为空；选择发生在 spec.admit。

原则 2

选择与观测分开

NodeAdmission.spec.machine 是持久的选择；NetworkEnrollment.status.observation.identity 是节点上报；两者不一致只提示，不自动改期望。

原则 3

标签是投影，不是真相

rlark.io/robot-model、station.rlark.io/machine-type 仍写给调度和 Addon 用，但 UI 的判定优先用 typed 字段。

原则 4

只在 astribot-owned 路径改

Station、station-gateway、Gateway 的 astribot_*.go、UI 的 src/astribot。NodeJoin 用 annotations，避免改 api/**。

03 · 发现

通用 SSH 候选是可选开关#

默认关闭，先单站点试点；候选只做无认证探测，不把账号发到 Hub。

在 SiteNetwork.spec.sites[].discovery 增加两个可选字段。现有 enabled、from、ranges、intervalSeconds 不变；关闭时行为与今天完全一致。

SiteNetwork / discoveryYAML
discovery:
  enabled: true
  intervalSeconds: 30
  from: { clusterID: rlark-local-dev-gpu, nodeName: cailiang }
  ranges: ["10.11.14.0/24"]
  includeUnclassified: true     # 新增；默认 false
  sshPorts: [22, 2222]              # 新增；默认 [22]，最多 4 个

Hub 探测什么

  1. 网络：站点声明的 ranges，加上 Hub 自己直连的私网；超过 /22 的网段只取 Hub 地址所在的 /22。公网、隧道、容器和集群网络不扫。
  2. 端口：class 的 entry 端口始终探测；开启通用发现时加上 sshPorts。
  3. 握手：只做 TCP + SSH key exchange，读取服务器 banner 和 host key，随后立即中止；不尝试用户名、密码或任何认证。
  4. 算法：优先 ED25519，其次 ECDSA，再到 RSA；同时记录 host key type，后续按同一算法固定，避免同一主机因 key 类型不同被误判为 HostKeyChanged。
  5. 分类：指纹命中 class 的照旧上报；未命中且开关开启的作为 unclassified 上报；没有 MAC 的主机不生成候选。

Machine 是候选记录，NodeAdmission 是每台机器持久的入网声明；status 只由 station-controller 写。

05 · 加入流程

机器人走 class，普通机器走 SSH#

同一个候选，两条路径，最后都落到 NodeAdmission.spec.machine 和节点观测。

Discovered有 SSH 证据；Robot 或 Unknown
→
Configuring选择类型、型号、凭据
→
Preflight / Inspect机器人登录 entry；服务器 SSH 预检
→
JoiningNodeOperation 或 NodeJoin
→
Joined节点上报，IdentityVerified
↘
Blocked / Failed重试或清除；清除后回到 Discovered

Gateway 可达性：直连 + Hub 认证中继

扫描发生在站点 Hub，Gateway 在管理面。只要求“Gateway 能直连”会把云站点/私网服务器排除在外，所以已定：Gateway 先尝试直连扫描到的地址，失败时通过 Hub 的认证中继连接。Hub 只转发 TCP，不接触账号；Gateway 仍是 SSH 客户端，NodeJoin 的预检、安装、重试和清除语义不变。

路径

直连优先，中继兜底

Gateway 先尝试目标地址；只有网络不可达/超时才走中继。认证失败、host key 不匹配、sudo 拒绝都直接报错，不应重试到中继掩盖问题。

认证

per-site token，不共享账号

中继 token 是站点级的短期/可轮换 Secret；Gateway 读取，station-controller 把它写进 Hub 的 Discovery 文档。Hub 常量时间比较，失败即关闭；token 不进日志。

范围

只到 discovery 的地址/端口

Hub relay 仍只允许站点发现范围内的目标；Gateway 不能借中继访问任意内网。目标验证和 station-controller 的 relay 共用同一套网络/端口规则。

部署

Gateway 必须能到 Hub relay 地址

中继地址沿用 Machine 的 entry.via（Hub 隧道地址:18022）；live 已验证 Gateway 容器可达 10.254.240.1:18022。其他站点必须保证同样可达；这是硬要求，不能用 direct-only 假设绕过。

已定 不再把“直连不可达 → 入网码”当主路径。 入网码只在直连和中继都失败时兜底。DocumentLevel 仍为 3：Discovery 文档增加中继 token；Release A 让 station-gateway 理解并支持认证中继，Release B 由 controller 写入 token。Gateway/UI 不需要用户额外填 relay 地址。

机器人：classified 与 unclassified

classified

指纹已命中 class

默认 Robot · s1u。管理员确认型号和 class 凭据，admit 写 {type: Robot, nodeClass: s1u, model: s1u}；station-controller inspection 通过后创建 NodeAdmission/NodeOperation。

unclassified

指纹未命中，但用户选机器人

只列出指纹包含该候选 key 的 Robot class；不匹配的型号置灰。加入后仍要登录 entry 读 serial、跳到 x86；失败就停在 CredentialRejected/NodeUnreachable，不会先创建 admission。

普通电脑 / GPU

  1. 选择“普通电脑/GPU”，地址、端口、host key 从候选预填；填账号、口令、可选 sudo、节点名。
  2. Gateway 立即预检：先直连，失败自动走 Hub 认证中继；中继只转发 TCP，不接触账号。只有直连和中继都不通时，UI 才提示入网码兜底。
  3. 预检通过后创建 NodeJoin：metadata label 指向 Machine，annotations 记录类型/型号/host key/algorithm/install labels。
  4. install 阶段调用 admitNode，写 NodeAdmission.Spec.Machine = {Server, model} 和安装标签；同时保留既有 class/serial，不整段覆盖。
  5. station-controller watch NodeJoin，把 Running/Failed/Succeeded 投影到 Machine.status.nodeJoin 和 phase；Gateway 不写 Machine.status。

06 · 节点自报

08 · 机器人型号

型号是目录，接入是 profile#

型号只增/删，不可编辑；新增只在后台 apply CRD，控制台只列表和删除。

把机器人型号从 NodeClass 里拆出来：RobotModel 是不可变的目录项，节点上报的 rlark.io/robot-model 必须能对上一个目录项；NodeClass.spec.model 引用它，继续负责 access、discovery、naming、uplink 和 addons。一个型号可以有多个接入 profile。

目录

只增/删，不编辑

新增只在后台通过 kubectl apply 写 RobotModel；控制台不提供新增和编辑，避免型号 ID 被改名后节点上报对不上。需要改名就删除后重建。

引用

型号 vs 接入 profile

RobotModel 是型号身份；NodeClass 是接入方式。同型号不同批次/网络可以有两个 class，但节点标签里的型号始终是同一个目录 ID。

后台新增：一条不可变的目录项

RobotModel · 字段与引用
字段 / 引用含义
metadata.name型号 ID，DNS label；写入节点 rlark.io/robot-model 和 observation，不可改
spec.displayName控制台显示名，例如 S1U；不可编辑
spec.vendor / description可选展示信息；不可编辑
NodeClass.spec.model引用一个 RobotModel；class 的 discovery/access/naming 仍归 class
节点 / observationrlark.io/robot-model 和 identity.model 必须是目录 ID，否则 UnknownModel
历史记录型号删除后，历史 Machine/Node 保留原字符串；UI 显示“未登记型号”，不自动猜

控制台：只列表和删除

场站节点 / 机器人型号
只读目录
型号 3 新增型号只能在后台 apply RobotModel；控制台不提供新增/编辑。
型号厂商 / 接入 profile使用操作
s1uS1U Astribot · 1 个 class 4 台节点 删除

没有“新增”和“编辑”；行内删除被引用时返回 409刷新

入口：场站节点页或扫描设置页的“机器人型号”链接；不新增原生侧边栏项，守住 astribot-owned 边界。

API：列表和删除，没有写入口

Gateway · admin-only
方法 / 路径行为
GET /api/v1/station/robot-models列出目录项、displayName、vendor、引用它的 class 数、在线节点数；不含 secret
DELETE /api/v1/station/robot-models/{name}删除未被引用的型号；被 NodeClass、节点记录（含离线）、Machine、NodeAdmission 或 NodeJoin 引用时返回 409，并列出引用
没有 POST / PUT / PATCH不提供新增/编辑；新增只在后台 apply CRD，spec 不可变
删除规则 可以删除，但被引用时先阻止。 型号被 NodeClass、节点记录（含离线）、Machine、NodeAdmission 或 NodeJoin 引用时返回 409；先移除/迁移节点和 class，再删除。没有 force；如果删除和节点上报并发，observation 会显示 UnknownModel，IdentityVerified=False，不会静默放行。

和入网、上报怎么对上

  • 入网下拉：机器人型号下拉只读 RobotModel 目录；选型号后再选接入 profile（NodeClass）。一个型号只有一个 profile 时自动选中。
  • 扫描候选：class 命中的候选显示目录里的 displayName；如果 class 的 model 不在目录里，UI 标“未登记型号”，机器人加入被阻止，直到后台补齐。
  • 节点上报：安装器写 rlark.io/robot-model=<目录 ID>；station-controller 对目录校验；不在目录 = UnknownModel，不伪装成已知型号。
  • 历史兼容：Release A 为现有 s1u 建目录项；legacy class 只有 rlark.io/robot-model 标签、没有 RobotModel 时，UI 显示“inferred”，并提示后台补目录项。
设计选择 为什么不把型号直接放在 NodeClass？ 型号是节点上报要对上的稳定 ID；NodeClass 是接入方式，可能因网络/批次/凭据不同而有多个。把两者分开，删除型号时才能准确判断“还有没有节点/class 在用”，也不会因为改 class 而改掉型号。

10 · 发布与安全

网关先行，两次发布#

DocumentLevel 2→3 不能和 controller 写新字段放在同一次发布；release stage 里 gateway 在 controller 之后。

Release A · 兼容

让 gateway 先懂 level 3

  • CRD/RBAC、station-api 新字段、station-gateway 能解析/宣告 level 3，并支持 Gateway 认证中继（token 由 Secret 提供，controller 暂不写）。
  • 内置 RobotModel s1u；legacy class 没有目录项时显示 inferred，后台补齐。
  • controller 仍写 level 2；includeUnclassified 不产生新文档字段。
  • 等所有 member 的 gateways-understand: 3 成立。
  • UI 可以先显示新字段，但开关保持关闭。
Release B · 启用

controller 写 level 3

  • controller 写 includeUnclassified/sshPorts/per-site relay token；gate 已满足。
  • 型号目录页可用：只列表/删除；新增型号仍只在后台 apply CRD。
  • UI 开关可用；默认仍关闭。
  • 先单站点试点，观察候选量、噪声、失败和 Gateway 可达性。
  • 再扩大到其他站点；机器人 S1U 流程保持原样。
回滚 CRD 先于 controller；回滚时不要有进行中的 admission/NodeJoin。 旧 CRD 会裁剪新字段；旧 controller 不认识 level 3 文档。两阶段发布是为了避免“旧 gateway 拒绝新文档”。

安全边界

  • Admin-only：所有扫描/入网接口仍在 requireAdmin 下；候选数据不跨站点/租户暴露。
  • 只扫私网：Hub 直连私网 + 声明 ranges；公网/隧道/容器/集群网络不扫。
  • 不向 Hub 发账号：探测只做 key exchange；机器人凭据只在 station-controller，服务器口令只在 Gateway 请求/内存。
  • 固定 host key：首次连接必须匹配扫描到的指纹和算法；变化不自动接受。
  • 中继最小授权：Hub relay 增加 Gateway 认证路径，只转发站点 discovery ranges/ports 内的 TCP；账号不离开 Gateway；目标不在范围直接拒绝。中继端点只在私网/隧道（或 TLS），不暴露公网明文 token。
  • 标签不可信：observation 是证据，不用于授权；服务器标签禁止 rlark.io/robot-*；banner 只作展示。

12 · 需要拍板

五个决策，决定后进 Release A#

Phase 0 只交付这份设计；这些决策确认后再写代码。

决策 01影响最大

普通服务器 SSH：Gateway 必须可达

已定：Gateway 先直连，失败走 Hub 认证中继；Hub 只转发 TCP，不接触账号。入网码只做最后兜底。

已定：Hub 认证中继 + Gateway 客户端；不再用 direct-only
决策 02拓扑

普通服务器加入后是 Hub 还是 Leaf？

现有 NodeJoin 的 declare 阶段总是声明为 Hub；每个 GPU 都成为 Hub 可能不是想要的结构。

推荐：v1 保持 Hub；Leaf 单独立项，不混进这次
决策 03范围

候选只做 L2，还是也做被路由的主机？

v1 用 MAC 作为 L2 证据；被路由的 GPU 不会成为候选，仍走手动 SSH/入网码。

推荐：v1 只做 L2；路由发现和 host-key 身份单独设计
决策 04证据

节点自报用标签/NodeInfo，还是硬件 attestation？

安装标签能抓漂移，但和入网选择同源；不是独立硬件证明。

推荐：v1 标签/NodeInfo + IdentityVerified；模型 Addon/硬件探测后续加强
决策 05型号目录

机器人型号：只增/删、不可编辑，新增只在后台？

RobotModel 作为稳定目录；控制台只列表和删除，新增只在后台 apply CRD；被 NodeClass/节点引用时禁止删除；节点上报未知型号显示 UnknownModel。

推荐：按此实现；Release A 内置 s1u，legacy class 标 inferred
Phase 0 结束条件 五个决策确认，且设计页评审通过。 之后进入 Release A：CRD/RBAC、station-api、station-gateway level 3 兼容、UI 字段；controller 仍写 level 2，等所有 gateway 理解 level 3 后再进 Release B。
